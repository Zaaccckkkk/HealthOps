# Routed assistant diagnostic evaluation

This suite measures the current Router -> clarification/resumption -> execution -> verification
path with a real configured model. It does not replace the frozen 30-question baseline or the
six earlier exploratory questions. The original prompt lock remains unchanged.

## Inputs and scenarios

The committed [question set](../src/api-service/eval/assistant_routed.synthetic.jsonl) contains
63 scenarios: 21 scenario templates repeated on the three imported synthetic accounts
(`synthetic-00000`, `synthetic-00003`, `synthetic-00001`). Repeated wording across accounts is
intentional: it tests different data availability, not 63 independent linguistic samples.
Every case freezes `today=2026-08-10` and `timezone=America/New_York`.

The [authoring source](../src/api-service/eval/build_routed_set.py) defines expected routes,
request specifications, missing fields and prewritten user replies. These are human-reviewable
expectations, not answers generated by the evaluated model. Review the gold before running.

| Scenario group | What it tests |
| --- | --- |
| Explicit, yesterday, last night | Metric and local-day resolution |
| Two metrics, seven-day window | Entire request covered, not only selected claims |
| Missing records | No records must not become zero |
| Period comparison | Separate current and earlier baseline windows |
| Availability | Inventory tool rather than a summary of one guessed metric |
| Resting heart rate | Avoid substituting general heart rate |
| Casual questions | Ask for missing metric/time/baseline before querying |
| Partial clarification | Retain earlier information and ask for remaining fields |
| Changed intent | New explicit request supersedes previous metric |
| Cancellation | Consume the pending conversation without calling the model |
| Unsupported requests | Refuse diagnosis, other-user access, invented values and unrelated tasks |
| Reference definition | Router and reference-tool selection only; not retrieval quality |

Examples:

- `How have I been doing recently?` -> clarification -> fixed simulated reply:
  `Show steps and sleep duration for the past 7 days.` Expected window: August 4–10 inclusive.
- `How did I sleep last night?` -> ask which metrics -> `Sleep duration and resting heart rate,
  please.` Expected date: August 9, following the application's start-day sleep convention.
- `How am I doing recently?` -> `Steps.` -> another clarification -> `Past 7 days.`
- `How are my steps recently?` -> `Actually, forget steps. Show sleep duration yesterday.`
  The final specification must contain sleep duration only.

All scenarios are diagnostic/development material. Do not use them for training and then report
performance on the same cases as held-out accuracy. A future held-out set should separate
scenario families and paraphrases; splitting these account duplicates randomly would leak wording.

## Router contract revision 2026-10-31.2

The model-facing `route_request` contract in
[routing.py](../src/api-service/healthops/assistant/routing.py) has seven required fields:
`decision`, `task`, `metrics`, `time_phrase`, `baseline_phrase`, `language`, and `reason`.
The schema inlines metric enums and the prompt supplies nine complete illustrative calls.
The model quotes user time phrases; Python resolves supported relative phrases and ISO dates,
then checks user grounding and date limits. Ambiguous scope still requires clarification.
Missing decisions and contradictory refusal reasons remain errors; no ready-state default is added.
The internal request specification remains compatible, with a new `router_version` marker.

The question set and grading rules are unchanged. Protocol tests use scripted outputs; only an
actual model run can establish whether this revised contract improves diagnostic accuracy.
See the [revision report](evidence/router-contract-v2.md) for local checks and historical
capacity blockers, and the [completed v2 retest](evidence/router-contract-v2-retest.md).

## Time parsing and execution contract revision 2026-11-01.1

Supported time phrases now tolerate a leading English article and terminal sentence punctuation
while retaining the original quote for user grounding. Execution-tool schemas inline enum
definitions, expose metric as a string, and provide complete argument examples. Malformed
metric objects are rejected with type-specific feedback rather than silently coerced.
The Router output marker and execution prompt version are `2026-11-01.1`; the Router prompt
itself is unchanged. The question set and grading rules remain frozen.
See [implementation, checks and live evaluation](evidence/execution-contract-v3.md).

## Running

From `src/api-service`, validate without a database or model:

```bash
uv run python scripts/eval_routed.py --validate-only
```

For real-model execution, first have the migrated local PostgreSQL database (including revision
0005), the imported synthetic cohort, the private frozen cohort baseline directory containing
`lock.json` and `questions.jsonl`, and a configured model endpoint. Use existing environment
settings for `HEALTHOPS_DATABASE_URL`, `HEALTHOPS_ASSISTANT_MODEL_BASE_URL`, model/backend and
limits. Do not put credentials in public commands or files.

```bash
uv run python scripts/eval_routed.py --cohort-dataset /absolute/private/baseline-directory --limit 2
# After inspecting the smoke-run artifacts, omit --limit for all 63 scenarios.
```

The runner accepts only a loopback database and `environment=local`. Loopback can also represent
a tunnel: the operator must ensure it targets the intended local synthetic evaluation database.
It does not create users, import data, migrate, provision, deploy or call the HTTP API. Model
requests use the configured endpoint and can incur charges if that endpoint is paid.

Identity preflight recomputes synthetic UUIDs from the existing frozen import manifest, checks
account labels and verifies original deterministic tool results against frozen gold. It never
accepts an arbitrary real-user UUID. New numerical gold is computed before model calls by the
existing deterministic Python tools using the independently authored metrics/windows. This
checks model use of tools; it is not an independent mathematical reimplementation of the tools.
Unit tests remain necessary for tool arithmetic correctness.

The runner invokes `RoutedAssistant`, including PostgreSQL-backed clarification state. Waiting
user replies are supplied by the fixture with the actual returned conversation ID/version.
Conversation metadata can be written/consumed; health observations are not changed. The existing
store may also clean expired clarification rows. Do not run this against a personal database.
A missing continuation blocks later turns; it never silently starts a new conversation.

## What passes

[eval_routed.py](../src/api-service/scripts/eval_routed.py) records checks separately:

1. Expected route and ready-state request specification (including all metrics and dates).
2. Clarification: missing fields, continuation ID/version, and no tool execution.
3. Execution: required primary tool, executed scope, and exact deterministic evidence match.
4. Cards and claims: rebuild cards from evidence, reverify claim references, compare rendered
   answer, and recompute coverage against the **gold** specification rather than model scope.
5. Verification: verified explanation, complete coverage, recorded verification attempts (one
   or two), and an answered/insufficient-data outcome.
6. Repair: first-attempt success and recovery when a real first verification failed.

A correct refusal or clarification does not require `explanation_status=verified`. A missing
record can still produce a correct verified answer. First tool is recorded diagnostically:
checking availability before the correct data tool is not automatically an error. Executing
only availability for a steps-summary request fails `primary_tool`, gold evidence and coverage.

A scenario passes only if **all planned turns** pass. Stage metrics show attempted-turn
numerators/denominators; blocked turns are reported separately and still make the scenario fail.
Repair recovery uses only naturally triggered repairs as its denominator. Zero repair cases
means no observed repair rate, not 100%. Guard rejection counts are diagnostic: recovery may
produce a successful final answer despite an initially rejected call.

Reference cases explicitly score routing/tool selection only. Retrieved relevance, corpus
coverage, quotation quality and clinical interpretation need a separate reviewed RAG evaluation.
A single aggregate must not be presented as full-system semantic accuracy.

## Evidence and limits

Private `.local/eval/routed-*/` outputs include prompt hashes, dataset/cohort lock hashes,
model metadata (digest/context when the adapter supplies them), settings, Git HEAD/dirty state,
runner hash, deterministic gold, responses, model proposals, per-turn latency and stage scores.
No raw health data or output reports are staged. A missing model digest is not a pinned model.
The runner records the current version; it does not assert equivalence to the old baseline.

Evaluator regression tests deliberately mutate otherwise valid scripted responses to catch
false passes: wrong route/tool, narrowed request, omitted metric, changed evidence/card, absent
verification, out-of-scope execution and invented answer. They also exercise actual routed
cancellation, blocked continuations, and the conditional repair denominator.
These are engineering tests, not Qwen accuracy measurements.

HTTP authentication, rate limiting, browser/iOS continuation delivery, database owner/CAS races,
expiry and injected tool/model failures are covered by separate application tests; this local
model benchmark does not establish their deployed correctness. The suite cannot prove that
all possible questions or failure modes are correct.

## Interaction generalization candidates

`eval/assistant_interaction.synthetic.jsonl` is a separate, reproducible set of **36 scenarios /
72 turns** (12 authored interaction templates across the three existing synthetic accounts).
It includes time-first and metric-first clarification, explicit multi-selection, correction after
selection, custom ISO dates, repeated ambiguity, changed intent, missing records, cancellation,
and unsupported fabrication requests. It contains questions and expected scope, not patient data.

Validate it from the API service:

```bash
uv run python scripts/eval_routed.py --cases eval/assistant_interaction.synthetic.jsonl --validate-only
```

The existing local and Cloud Run HTTP evaluators accept this case format through `--cases`.
Real runs still require the frozen cohort, synthetic identity proof and configured model.
These cases have **not been run on Qwen**. They are generalization candidates, not an independently
collected benchmark or an accuracy result. Keep them out of training; if used for prompt tuning,
relabel them diagnostic and reserve new questions for evaluation.
